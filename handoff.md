# Handoff — laro_mvp_tracker

Estado do projeto, comandos e armadilhas para quem continuar. Atualizado junto das mudanças estruturais.

## O que é

Bot Discord de tracker de MVP (Ragnarok LATAM) em Python 3.13-3.15, rodando em Docker na VM Oracle `laro-vnic` (VM.Standard.E2.1.Micro, Ubuntu 24.04, ~1 GB RAM). Postgres 16 em container no mesmo compose. Repo público: `EduardoSFragoso/laro_mvp_tracker`.

## Estrutura

```text
src/
    app.py                  # entrypoint (bot + timers + health server)
    laro/
        command/            # comandos !foo (dispatcher em event/on_message.py)
        event/              # handlers de eventos (on_ready, on_message, ...)
        service/
            channel_service.py  # lifecycle, painel e limpeza do canal
            tracking_service.py # resolução de MVP e gravação de rastreios
            event_service.py    # eventos WOE (TypedDicts de weekly_event.py)
            monitoring_service.py  # /health + heartbeat (HEARTBEAT_URL)
        ui/
            channel_views.py    # views, botões, select e modal do Discord
        timer/              # event_timer (avisos de respawn)
        util/               # track_util (cálculo de janelas de respawn)
sql/                        # schema + seed LATAM (usado na 1a subida do volume)
Dockerfile                  # python:3.15.2-alpine
docker-compose.yml          # db + bot + autoheal
.github/workflows/ci.yml    # CI: checks (3 Pythons) + types (pyright) + audit
docs/                       # auditoria-infra, configuracao-repositorio, decisoes, hosting-oracle
pyrightconfig.json          # basic mode, venvPath .venv, src+tests
```

## Contratos que não podem quebrar

- `/health` deve responder **503** até `tracker_ready` e **200** depois (autoheal e o docker healthcheck dependem disso). `HEALTH_PORT=0` desliga o servidor de health (conta como saudável).
- Heartbeat: `monitoring_service.run_heartbeat` pinga `HEARTBEAT_URL` a cada `HEARTBEAT_SECS` (60s). Monitor: healthchecks.io (period/grace 10 min) → e-mail `duds.fragoso@gmail.com`.
- Aviso de janela de respawn: **mensagem viva** (`ChannelState.notification_message`, título `:bell: Janelas de respawn abertas`) — fica no canal enquanto houver janela aberta (`r1 <= 0 <= r2`) e é deletada quando a última fecha. Exceção na limpeza (`is_msg_can_be_deleted`); no restart, `init_channel` re-adopta o aviso existente e apaga duplicados. Ping só em **janela nova**, na role `guild.id_notification_role` (`!setpingrole`/`!unsetpingrole`); **nunca** `@here`/`@everyone` (`AllowedMentions.none()` ou `roles=[role]`).
- Flag de aviso persistida: coluna `mvp_guild.notified` (NOT NULL, default FALSE) — gravada `TRUE` quando o aviso sai, `FALSE` ao re-rastrear (`update_track_time`) e restaurada em `load_db_entries` (restart não re-pinga janela já avisada).
- Gate de admin: `ADMIN_COMMANDS` em `event/on_message.py` (`!timezone`, `!unsettimezone`, `!setmvpchannel`, `!unsetmvpchannel`, `!setpingrole`, `!unsetpingrole`, `!clean`, `!mobile`) exigem a permissão **Gerenciar Servidor** do usuário. `!track`, `!woe` e `!settings` (leitura) ficaram abertos.
- Botões de confirmação de `!clean` e `!setmvpchannel`: só o administrador que iniciou a ação pode confirmar ou cancelar, e ele precisa manter **Gerenciar Servidor** até interagir.
- Menções são desativadas por padrão no cliente Discord (`AllowedMentions.none()`); o ping explícito da role de notificação continua permitido quando configurado.
- Docker instala `src/requirements.lock`; ao atualizar dependências, manter o lockfile coerente com `src/requirements.txt`. `.dockerignore` exclui `.env`, arquivos de chave privada e diretórios locais de desenvolvimento.
- Painel do canal de tracking: embed amarela única com `title` 👑 MVPs + `thumbnail`; `!mobile` alterna entre 3 colunas e layout 1 coluna. Discord **não** permite `#` headers nem fonte custom em embed (testado em 2026-11; preview de 2 embeds foi rejeitado pelo dono — manter formato atual).
- `on_ready` reutiliza `bot.pool` após reconexões do gateway; não criar pool substituto sem fechar o atual. `tracker_ready` volta a `False` enquanto a conexão é revalidada.
- `app.main` supervisiona os workers com `asyncio.TaskGroup`, fecha o cliente e o pool na saída; falha fatal ao inicializar o banco fecha o bot e deixa o healthcheck sinalizar a indisponibilidade.
- `update_track_time` grava entrada e histórico com `ON CONFLICT` dentro de uma transação; atualiza o estado em memória somente após o commit.
- Alterações de configuração de servidor persistem no banco antes de atualizar o estado em memória; remover um servidor apaga os dados relacionados em uma única transação.
- Componentes de interação do canal ficam em `laro/ui/channel_views.py`; callbacks importam o serviço localmente para evitar ciclo de importação.
- `run_coro` captura falhas esperadas da API Discord. Erros de programação propagam para o chamador e ficam visíveis.
- O bot roda como usuário sem privilégios no container. O `autoheal` usa versão fixada e não precisa de rede; no deploy, atualizar essa imagem e recriar `bot` e `autoheal` conforme o comando acima.
- Notificação só marca `notified` depois que o envio/edição no Discord funciona. `notification_pending` vive apenas em memória e permite nova tentativa enquanto a janela continua aberta.
- `bot.guild_states: dict[int, GuildState]` — ao remover servidor, `pop(id, None)`; nunca armazenar `None` (quebra `on_ready`).
- Comandos via DM são ignorados (`message.guild is None` → return).
- `.env` nunca lido/commitado pelo agente (AGENTS.md). `.env.example` é o contrato de nomes.

## Armadilhas conhecidas

- `bot.user` e `message.guild` podem ser `None` — todos os handlers atuais já têm guard; pyright basic pega regressões.
- Na VM, `GUILD_ID` vazio crasha (corrigido na PR #9: env vazias viram defaults); o valor real está no `.env` da VM.
- O pyrightresolve imports via `.venv` (`venvPath`); em CI o job `types` cria `.venv` e instala também `pytest` (não está no lockfile).
- VM E2.1.Micro tem 1 GB RAM — cuidado com sidecars pesados (autoheal ~10 MB, ok).
- `.env` da VM: senha do Postgres definida manualmente no setup (símbolos `$`, `@`, `:/` perigosos em shell); guardada no gerenciador de senhas do dono.
- `cron` não vem instalada na VM Ubuntu (miniatura Oracle): `sudo apt install cron` antes de criar crontab.
- Colunas novas do esquema: `guild.id_notification_role` e `mvp_guild.notified` (NOT NULL default FALSE). Um banco/volume criado antes dessas features quebra o load (`db_guild['id_notification_role']` via `SELECT *`). Migração manual: `ALTER TABLE guild ADD COLUMN IF NOT EXISTS id_notification_role bigint;` e `ALTER TABLE mvp_guild ADD COLUMN IF NOT EXISTS notified boolean NOT NULL DEFAULT FALSE;`
- Local (Windows): o `db` não publica porta (só existe na rede do compose; acesse com `docker compose exec db psql ...`). Se descomentar o `ports` p/ dev, o bind em `127.0.0.1:5432` pode falhar por faixa reservada do WinNAT/Hyper-V ("bind: ... proibida pelas permissões de acesso").

## Resiliência (como está em produção)

| Camada | Proteção |
|---|---|
| Crash (processo morre) | `restart: unless-stopped` |
| Travado (healthcheck unhealthy) | container `laro-autoheal` reinicia (varre a cada 60s) |
| Tudo morto / VM fora | healthchecks.io → e-mail |
| VM sobrecarregada | alarme Oracle `laro-cpu-alta` (CpuUtilization > 80% por 10 min) → tópico `alertas-laro` → e-mail |
| Perda do volume do banco | `~/backup_laro.sh` na VM, cron `0 4 * * *`: dump+gzip → OCI `laro-db-backups` (objeto único via PAR de escrita) → rotação local 7 dias → ping no healthchecks `backup-laro` (grace 1h). URLs secretas em `~/.laro_par_url` e `~/.laro_backup_hc_url` (600, fora do repo). Detalhes: `docs/auditoria-infra.md` seção 2 |
